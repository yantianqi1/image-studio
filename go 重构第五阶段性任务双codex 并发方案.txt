# 两路并发开发方案

你现在可以把 Codex 拆成两路：

```txt id="parallel-map"
Codex A：第五阶段主线
目标：Go Core API / 商业核心 Go 化

Codex B：下一步并行线
目标：Go Runtime 生产化 / 运维控制面 / 性能与灰度
```

这样拆的好处是：

```txt id="why-parallel"
A 负责业务核心：identity、billing、quota、provider、pricing
B 负责运行平台：worker control plane、metrics、runbook、压测、灰度、Python legacy 清理
```

两路可以并行，因为主要改动目录不同。当前仓库已有 `apps/worker-go`，Go module 是 Go 1.23，并使用 `pgx/v5`。 当前执行模型也已经有 `image_job_items`，并带 queue pick、job result、running lease 相关索引。
建议新增 `go.work` 管理多个 Go module；Go 官方文档说明 `go.work` 的 `use` directive 可以让多个 module 在同一 workspace 中作为 main modules 一起构建和开发。([go.dev][1])

# 合并顺序

建议：

```txt id="merge-order"
1. 先合 Codex A 的 runtime-go 基础结构和 core-api-go skeleton
2. 再合 Codex B 的 worker control / observability
3. 最后合统一 go.work、CI、docker-compose 变更
```

如果两个 Codex 都需要改 `go.work`、`.github/workflows/*`、`docker-compose.yml`，让 Codex B 暂时只输出 patch 说明，不直接提交这些共享文件，等 A 合并后再统一处理。
