# Comic Character Reference Consistency Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Build a real character-reference pipeline so comic pages reuse generated character sheets instead of relying only on text prompts.

**Architecture:** After the LLM creates `ComicCharacterCard` rows, the system enqueues one reference image job per character using `multi_view_prompt`, stores the completed asset on the character card, and blocks page image generation until required reference assets are ready. Page generation then sends the panel prompt plus relevant reference asset IDs to the image adapter.

**Tech Stack:** FastAPI, SQLAlchemy, Alembic, PostgreSQL, existing `image_jobs` worker, OpenAI-compatible image adapter, pytest, Next.js frontend.

---

## Why This Exists

The current comic pipeline can generate a completed comic page, but character identity consistency is only a text-prompt convention. In one generated page, the same character can look different between upper and lower panels because the image provider receives no canonical visual reference. The fix must create a real reference asset pipeline, not just add stronger wording.

## Current Facts

- `ComicCharacterCard` already stores `must_keep_prompt`, `negative_prompt`, `multi_view_prompt`, `reference_image_job_id`, and `reference_asset_id`.
- `multi_view_prompt` is generated by the LLM but is not consumed by page generation.
- `reference_image_job_id` and `reference_asset_id` are currently empty after a successful E2E run.
- Page prompts include `must_keep_prompt`, but no image reference assets.
- `image_jobs` currently supports `source_asset_id` for edit mode, not multiple reference assets for generate mode.
- Frontend currently can imply agent progress even when only a project exists.

## Target Behavior

1. Completing a comic LLM task creates story analysis, character cards, storyboard, and panel prompts.
2. A dedicated character-reference approval endpoint enqueues one image job per character card.
3. Each character reference job uses `multi_view_prompt` to generate a multi-view character sheet.
4. Completed reference image assets are synced to `ComicCharacterCard.reference_asset_id`.
5. Comic page image approval fails explicitly until required character references are ready.
6. Page image jobs store and pass all relevant reference asset IDs to the renderer.
7. Page prompts include strict identity-lock instructions that cite attached reference sheets.
8. Frontend reflects real states only; no fake agent progress when no task exists.

## Execution Order

1. Backend A: image job reference storage and adapter propagation.
2. Backend B: comic character reference endpoints and page generation gating.
3. Frontend and E2E: real UI states plus manual production-like verification.

## Acceptance Criteria

- Character reference sheets are generated as real image jobs, not just text fields.
- Page generation refuses to run without required character references.
- Page generation sends all relevant reference assets to the provider path or raises an explicit unsupported-provider error.
- No silent fallback drops reference assets.
- `multi_view_prompt` is no longer dead data.
- Frontend no longer implies a real agent is running when only a project exists.
- Focused backend tests, frontend typecheck, migration upgrade, and manual safe E2E all pass.
